# Небольшие итерации Stackr

## 3 ноября 2026 — приглашения в приватный контест

Реализовано:
- Гость открывает карточку приглашения без входа. Закрытые задачи и токен организатора в ответ не попадают.
- Вход и создание аккаунта возвращают к исходному приглашению.
- Участник вступает явным действием; контест становится доступен в его списке.
- Организатор может заменить ссылку с подтверждением. Старая ссылка прекращает работать, доступ уже вступивших сохраняется.
- Ошибка копирования не отображается как успешное копирование; добавлены пояснения для организатора.

Проверено: 95 серверных тестов (в том числе 10 тестов контроллера контестов), сборка TypeScript/Vite, ESLint, типизация браузерных тестов. Добавлен отдельный браузерный сценарий `web/e2e/invitation.spec.ts` с desktop/mobile скриншотами.

Живая браузерная проверка выполнена 3 ноября 2026: `bash scripts/e2e.sh invitation.spec.ts` — 1 сквозной тест прошёл. Проверены гостевой просмотр, регистрация с возвратом, вступление, вход организатора с возвратом, замена ссылки и HTTP 404 старого приглашения. Проверен экран 390 px без горизонтального переполнения. Все четыре сервиса Compose healthy.

## 3 ноября 2026 — восстановление после остановки сервисов

Воспроизведено: при остановленном runner DNS окружения выдавал 240.0.0.44 вместо адреса Compose; Java сохраняла этот ответ и продолжала получать EOF после запуска runner. Проверка отдельным Java-процессом показала сохранение неправильного адреса на протяжении всех 12 замеров. Прямые HTTP-запросы к уже работающему runner успешно возвращали AC.

Исправлено: TTL успешного и отрицательного DNS-ответа Java установлен в 1 секунду, использование устаревшего ответа отключено. Для внутреннего имени runner добавлена проверка адреса перед запросом. Nginx также обновляет адрес API через Docker DNS вместо сохранения адреса на весь срок работы процесса.

Проверено на реальном Compose:
- остановка runner → ERROR, рейтинг не изменился;
- запуск runner без перезапуска API → пять TLE и последующий AC;
- шесть одновременных отправок → пять приняты, одна отклонена лимитом;
- пересоздание API без перезапуска web → HTTP API доступен через nginx;
- 95 серверных тестов прошли без ошибок и пропусков.

Настройки сверены с [документацией Java 21](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/doc-files/net-properties.html) и [документацией nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass). Это проверка конкретных отказов, а не полный нагрузочный или security-аудит.

Финальная браузерная проверка этапа: 3 сценария прошли — приглашение с регистрацией и заменой ссылки, Java-редактор с пользовательским вводом/черновиком/реальным AC, главная и вход без JavaScript-ошибок.

## 5 ноября — логика пользовательских переходов

Повторный общий прогон: 29 сценариев Chromium прошли за 28 секунд. Включены две новые регрессии: вход по защищённой прямой ссылке возвращает на исходную задачу с contestId; приглашение чужому организатору объясняет роль и не предлагает недоступное управление контестом.

Исправления: защищённые страницы участника/организатора сохраняют адрес возврата при входе; у чужого организатора убрана ведущая к 403 кнопка приглашения; незарегистрированному пользователю завершённого приватного контеста больше не обещаются недоступные результаты. При смене ID контеста очищаются предыдущие данные и состояния, поздний ответ предыдущего запроса игнорируется. В гостевой мобильной навигации скрыта пустая строка.

Проверены сборка Vite/TypeScript, ESLint, весь набор браузерных сценариев и автоматическая доступность основных экранов. QA после прогона архивированы. Это конечный набор проверок, не гарантия отсутствия всех возможных ошибок.
