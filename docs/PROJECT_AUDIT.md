# Аудит Stackr Java

Дата: 2 ноября 2026 года. Исходник: архив `stackr-java.zip`, предоставленный пользователем. Рабочая копия распакована в рабочем каталоге чата; исходный ZIP и перенесённая пользователем папка не изменялись.

## Что обнаружено

| Область | Реализация в архиве | Состояние при первичной проверке |
|---|---|---|
| API | Java 21, Spring Boot 3.2.5, Spring Security/JWT, JPA | Основной код компилировался; тестовый код не компилировался |
| База | PostgreSQL 15, четыре миграции Liquibase | Первоначальные интеграционные тесты обходили миграции через H2 create-drop |
| Учётные записи | Регистрация, вход, refresh, роли, профиль, смена пароля | В архиве уже были незакоммиченные исправления типов JWT; они сохранены |
| Задачи | Каталог, темы, условия, шаблон, публикация, тесты, подсказки | Права организатора не везде проверяли принадлежность ресурса |
| Посылки | Отправка, история, polling, клиент runner | Запуск проверки до commit; UI прекращал ждать после короткого интервала |
| Проверка Java | Отдельный runner, компиляция один раз, тесты, сравнение вывода | DockerService запускал javac/java напрямую в процессе сервисного контейнера; оценка памяти была выдуманной |
| Контесты | Создание, приглашения, регистрация, standings, analytics | Не все ограничения отправки проверялись; переход к задаче терял contestId |
| Интерфейс | React/TypeScript, Monaco, страницы участника и организатора | Сборка проходила; полноценная браузерная приёмка отсутствовала |
| Развёртывание | Dockerfile API и runner, Compose с PostgreSQL | Интерфейс не входил в Compose; runner был опубликован на хост |
| Тесты | JUnit, Mockito, H2, интеграционные HTTP-тесты | Устаревшие сигнатуры, ошибки generic-типов, неопределённая переменная, устаревшие ожидания ролей |

Старое описание навыка упоминало Redis и Flyway. В фактическом исходнике они не используются; заменять Liquibase или добавлять Redis без необходимости не требуется.

## Выполненные изменения

- Исправлены ошибки тестового кода и ожидания, устаревшие относительно реального поведения: автор может удалить свою задачу, организатор может отправить проверочное решение, refresh требует REFRESH-токен.
- Добавлен корректный HTTP 401 для запроса без аутентификации.
- Проверки организатора для тестов, подсказок и списков посылок привязаны к автору задачи; доступ к чужому исходному коду ограничен владельцем, автором задачи и ADMIN.
- Ограничен прямой доступ к черновикам и приватным контестам; задачи предстоящего контеста скрыты из его карточки для обычного участника.
- Добавлены временные границы, регистрация и принадлежность задачи для контестной посылки; неверный интервал соревнования отклоняется.
- Исправлен запрос посылок контеста: используется contestId, а не problemId.
- Повторный AC не увеличивает баллы за одну и ту же задачу; число попыток учитывает и неудачные решения, исключая инфраструктурные сбои.
- Посылки подбираются из БД после commit; добавлена миграция индекса очереди. Незавершённая транзакция откатывается при остановке, запись остаётся PENDING.
- Компиляция и каждый тест запускаются в отдельных Docker-контейнерах без сети, под непривилегированным UID, с read-only root, ограничениями CPU, памяти, процессов, вывода и времени. Между фазами используется именованный том с классами, при исполнении read-only.
- Ввод, stdout и stderr обслуживаются параллельно, чтобы заполнение pipe не обходило таймаут; диагностические сообщения ограничены.
- Добавлен ERROR для сбоев инфраструктуры; такие ошибки не превращаются в RE участника и не увеличивают штрафы/число неправильных попыток.
- Убрана фиктивная статистика памяти. Пользователь видит сообщения компилятора, но не stderr скрытых тестов.
- В Compose добавлен web/nginx, проверки готовности, локальная привязка опубликованных портов; runner и PostgreSQL не публикуются на хост.
- Добавлены генерация локальных секретов без перезаписи, .dockerignore, пример окружения и scripts/dev.sh.
- Monaco обслуживается локально; экран решения загружается отдельным модулем. Контекст контеста сохраняется в ссылке и посылке, история сортируется от новых к старым, polling продолжается для PENDING.
- Добавлены проверки прав на тесты, подбора очереди, применения миграций, границ контеста, повторного AC и Docker-изоляции; HTTP smoke-сценарий для реальных вердиктов.

Это перечень изменений кода. Какие проверки реально выполнены и какие пропущены, указано в VALIDATION.md.

## Что требуется до полноценного выпуска

1. Пройти сквозную браузерную приёмку всех ролей, включая отрицательные сценарии и обновление сессии.
2. Привести весь интерфейс к единой визуальной системе. Начать с экрана решения и редактора, затем каталог, контесты, профиль и кабинет организатора. Критерии в STACKR_PLAN.md.
3. Зафиксировать единые правила результатов: ICPC-подобная standings и старый балльный leaderboard сейчас представляют разные модели; необходимо согласовать штрафы и отображение во всех местах.
4. Проверить часовую зону и перейти к однозначному хранению/передаче времени; сейчас используется LocalDateTime.
5. Доработать список собственных черновиков организатора и список приватных контестов, на которые уже приглашён участник.
6. Проработать удаление задач и соревнований с посылками, обработку конфликтов БД и сообщений в интерфейсе.
7. Проверить достаточность лимита двух параллельных запусков runner, настроить квоты посылок и общий бюджет проверки; проверить нагрузку и восстановление после падений.
8. Подготовить резервное копирование, восстановление, диагностические метрики, управление административной ролью и обновление зависимостей.
9. После устойчивого основного сценария развивать тематические учебные треки и содержательное наполнение.

## Граница текущего этапа

Первый этап делает исходник проверяемым и готовит воспроизводимый локальный запуск. Он не объявляет завершённым редизайн, внешнее размещение, нагрузочную проверку или все требования НИР. Точное состояние подтверждается результатами запуска.
